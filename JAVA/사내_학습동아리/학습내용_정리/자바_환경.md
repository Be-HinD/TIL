## 2. JVM (WORA)

> **Write Once Run Anywhere**
>
> "JVM은 Java와 OS 사이의 통역사."

### 실행 흐름
소스코드          컴파일러       바이트코드        런타임
Hello.java  →   javac   →   Hello.class  →   JVM  →  실행
(사람이 읽는 코드)              (중간 언어)       (OS별 통역)

### JVM이 하는 일 3가지

1. **바이트코드 해석 및 실행** — `.class`를 OS가 이해하는 기계어로 변환
2. **JIT 컴파일** — 자주 쓰는 코드는 기계어로 캐싱해서 성능 확보
3. **메모리 관리(GC)** — 개발자가 직접 메모리 해제 안 해도 됨. C의 `free()` 불필요

### JVM Deep

> "JVM은 결국 C/C++로 작성된 프로그램이다."

- 가장 많이 쓰는 JVM인 **HotSpot JVM**은 Oracle이 C++로 만든 실행파일
- `java` 명령어 자체가 JVM 프로세스를 띄우는 것
- JVM은 `.class`로 된 바이트코드를 실행할 뿐
- 바이트코드를 만드는 건 `javac` 명령어를 통해 수행

> **컴파일과 실행은 별개의 주체가 수행한다.**

## 3. 용어 정리: JDK vs JRE vs JVM

| 용어 | 이름 | 설명 |
|---|---|---|
| JDK | Java Development Kit | 자바 개발 도구 (`javac` 포함) — 우리가 설치할 것 |
| JRE | Java Runtime Environment | 실행 환경 (JVM 포함) |
| JVM | Java Virtual Machine | 실제 자바를 돌리는 가상 머신 |

> ⚠️ Java 11부터는 JRE 별도 배포를 하지 않으니 참고.

**비유:** 요리 도구 세트(JDK) / 주방 시설(JRE) / 요리사(JVM)

### 도식화
┌─────────────────────────────┐
│           JDK               │
│  (개발 도구 전체 패키지)       │
│                             │
│  javac, javadoc, jar ...    │
│                             │
│  ┌───────────────────────┐  │
│  │         JRE           │  │
│  │    (실행 환경)          │  │
│  │                       │  │
│  │  ┌─────────────────┐  │  │
│  │  │      JVM        │  │  │
│  │  │  (실제 실행 엔진) │  │  │
│  │  └─────────────────┘  │  │
│  └───────────────────────┘  │
└─────────────────────────────┘

> **JDK만 받으면 모든 환경 구성은 완료.**

## 4. 자바 TMI

### javax → jakarta 네임스페이스 변경

Oracle이 Java EE를 Eclipse 재단에 넘기면서 문제가 생김.

Oracle이 `javax` 네임스페이스 상표권을 포기하지 않음 → Eclipse 재단은 `javax`를 쓸 수 없게 됨 → `jakarta`로 변경

| 구분 | 네임스페이스 | 관리 주체 |
|---|---|---|
| Java EE (~ 2019) | `javax.*` | Oracle |
| Jakarta EE (2019~) | `jakarta.*` | Eclipse 재단 |

**Spring Boot 기준**

| 버전 | 네임스페이스 | 비고 |
|---|---|---|
| Spring Boot 2.x | `javax.*` | |
| Spring Boot 3.x | `jakarta.*` | Java 17 필수 |

```java
// 구버전 (javax)
import javax.servlet.http.HttpServletRequest;
import javax.persistence.Entity;

// 신버전 (jakarta)
import jakarta.servlet.http.HttpServletRequest;
import jakarta.persistence.Entity;
```

> 패키지 이름만 바뀐 거라 기능 차이는 없음.  
> 단, 마이그레이션 시 import 전부 바꿔야 해서 레거시 프로젝트엔 꽤 고통스러운 작업.

### 구조 관계도
┌─────────────────────────────────────┐
│  Java SE (언어 + JVM)                │
│  Oracle 관리                         │
│  "Java 언어 자체"                    │
└─────────────────────────────────────┘
↓ 기반으로
┌─────────────────────────────────────┐
│  Jakarta EE (웹 개발 표준 스펙)       │
│  Eclipse 재단 관리                   │
│  "웹 개발할 때 이렇게 만들자"         │
└─────────────────────────────────────┘
↓ 스펙을 구현
┌─────────────────────────────────────┐
│  Spring, Tomcat 등 (구현체)          │
│  각 회사/커뮤니티 관리               │
│  "스펙대로 실제로 만든 것"           │
└─────────────────────────────────────┘

| 기술 | 관리 주체 | 역할 |
|---|---|---|
| Java SE | Oracle | 언어 문법, JVM, javac |
| Jakarta EE | Eclipse 재단 | 웹 개발 표준 인터페이스 |
| Spring | VMware | Jakarta EE 스펙 구현 |
| Tomcat | Apache | 서블릿 스펙 구현 |

> Oracle이 Java EE를 Eclipse에 넘김 → Eclipse는 `javax` 상표권을 못 받음 → `jakarta`로 네임스페이스 변경 → Spring/Tomcat 등 구현체들이 전부 따라감

### Java는 Oracle 것이 아닌가?

**흐름 정리**

1. 1995년 **Sun Microsystems**가 Java 만듦
2. 2006년 Sun이 Java를 오픈소스로 공개 → **OpenJDK** 탄생
3. 2010년 **Oracle이 Sun을 인수** → Java 소유권 + OpenJDK 둘 다 Oracle 손에

> "Oracle이 Java 만든 게 아니라 Java 만든 회사(Sun)를 사버린 것."

**왜 OpenJDK가 베이스냐**

Sun이 이미 오픈소스로 공개해버렸기 때문에 Oracle이 인수해도 되돌릴 수 없었음.
Sun이 오픈소스 공개 (2006)
→ Oracle이 인수 (2010)
→ OpenJDK는 이미 오픈소스
→ Oracle도 OpenJDK 기반으로 Oracle JDK 빌드

## TMI: IDE?

> "Integrated Development Environment — 통합 개발 환경"
>
> 한 줄 요약: **코드 작성 조무사**

### IDE가 하는 것들

| 기능 | 설명 |
|---|---|
| 코드 자동완성 | `Sys` 치면 `System.out.println` 추천 |
| 오류 표시 | 컴파일 전에 빨간줄로 미리 알려줌 |
| 빌드/실행 | `javac`, `java` 버튼 하나로 해결 |
| 디버깅 | 코드 중간에 멈춰서 변수값 확인 |
| Git 연동 | 코드 버전 관리 내장 |
| 리팩토링 | 변수명 전체 일괄 변경 등 |

### 언어별 IDE

| 언어 | IDE |
|---|---|
| Java | IntelliJ, Eclipse |
| Python | PyCharm, VSCode |
| C/C++ | Visual Studio, CLion |
| Swift | Xcode |

### VSCode가 여러 언어를 지원하는 이유

VSCode는 IDE가 아니라 **텍스트 에디터 기반**이라 구조가 다름.  
언어 지원을 플러그인으로 갈아끼우는 구조 → 지원은 되지만 언어별 전용 기능은 약함.

> **전용 기능 예시:** IntelliJ는 `.class` 파일을 열면 자동으로 Java 코드로 역컴파일해서 보여줌 (VSCode는 안 됨)

### IDE가 하나의 언어만 전폭 지원하는 이유

언어마다 아래 요소가 전부 다르기 때문:

| 요소 | 이유 |
|---|---|
| 문법 분석기 (Parser) | Java 문법과 Python 문법이 완전히 다름 |
| 빌드 시스템 연동 | Java는 Gradle/Maven, Python은 pip |
| 실행 환경 연동 | Java는 JVM, Python은 인터프리터 |
| 자동완성 엔진 | 언어별 타입 시스템이 다름 |
| 디버거 | 언어별 디버그 프로토콜이 다름 |
