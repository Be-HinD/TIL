# 예외 설계 명세

> **적용 범위**: Spring Boot
> **참고 표준**: [RFC 9457 – Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457)

---

## 1. 예외 계층 구조

```
RuntimeException
└── BusinessLogicException          ← 서비스 레이어 예외 기반 클래스
    └── (선택적 상속 구현체)           ← 후처리가 필요한 예외만 생성
        예) FileUploadException, ...

RuntimeException
└── ExternalApiException            ← 인프라 레이어 예외 기반 클래스
    └── BitbucketApiException       ← 외부 시스템별 구현체

AuthenticationException (Spring Security)
└── SecurityAuthException           ← 보안 필터 레이어 예외 기반 클래스
    └── (선택적 상속 구현체)           ← 후처리가 필요한 예외만 생성
        예) TokenExpiredException, ...    
```

### 1.1 계층별 책임 원칙

| 레이어 | 예외 클래스 | 책임 |
|---|---|---|
| 서비스 | `BusinessLogicException` | 도메인 규칙 위반, 비즈니스 흐름 오류 |
| 인프라 | `ExternalApiException` | 외부 API 호출 실패, 기술적 장애 |
| 보안 필터 | `SecurityAuthException` | JWT 검증 실패, 인증 컨텍스트 미설정 |

## 2. 서비스 레이어 예외

### 2.1 BusinessLogicException

```java
@Getter
public class BusinessLogicException extends RuntimeException {

    private final ErrorCode errorCode;
    private final String detail;
    private final Object data;

    // 생성자 오버로딩 1: 상세 + 데이터 포함
    public BusinessLogicException(ErrorCode errorCode, String detail, Object data) { ... }

    // 생성자 오버로딩 2: 데이터 생략
    public BusinessLogicException(ErrorCode errorCode, String detail) { ... }

    // 생성자 오버로딩 3: detail, data 모두 생략
    public BusinessLogicException(ErrorCode errorCode) { ... }
}
```

### 2.2 ErrorCode 열거형

개별 예외 클래스 남발로 인한 클래스 수 폭발을 방지하기 위해, 도메인 예외 종류는 `ErrorCode` 열거형으로 일괄 관리한다.

```java
public enum ErrorCode {

    NOT_FOUND_USER(
            "U001",
            "사용자를 찾을 수 없습니다",
            HttpStatus.NOT_FOUND,
            "/errors/user-not-found"
    ),

    EXPIRED_TOKEN(
            "A004",
            "토큰이 만료되었습니다",
            HttpStatus.UNAUTHORIZED,
            "/errors/token-expired"
    );

    private final String code;       // 클라이언트 분기 처리용 내부 식별자
    private final String title;      // RFC 9457 title: 에러 종류의 고정 요약
    private final HttpStatus httpStatus;
    private final String typeUri;    // RFC 9457 type: 에러 종류를 식별하는 URI
    // 현재 백오피스 환경에서는 공개 문서가 없으므로 about:blank 사용
    // 향후 Confluence 에러 문서 작성 시 해당 URL로 교체 가능
}
```

**ErrorCode 코드 체계 (prefix 기준)**

| Prefix | 도메인             |
|--------|-----------------|
| `U`    | User            |
| `A`    | Auth            |
| `P`    | Project         |
| `J`    | Jenkins         |
| `B`    | SCM (Bitbucket) |
| `C`    | Common / 공통     |

### 2.3 상속 구현체 생성 기준

원칙적으로 `BusinessLogicException`에 `ErrorCode`를 주입하는 방식으로 처리한다.  
아래 **두 조건 중 하나** 해당 시에만 상속 구현체를 생성한다.

1. `RestControllerAdvice` 핸들러에서 **별도 후처리 로직**이 필요한 경우
2. 동일 `ErrorCode` 내에서 **처리 방식이 케이스마다 달라지는** 경우

```java
// 상속 구현체 예시 - 핸들러에서 별도 처리 필요 시
public class FileUploadException extends BusinessLogicException {
    private final String fileName;

    public FileUploadException(String fileName) {
        super(ErrorCode.FILE_UPLOAD_FAILED, "파일명: " + fileName);
        this.fileName = fileName;
    }
}
```

### 2.4 사용 예시

```java
// 기본 사용 - ErrorCode만
throw new BusinessLogicException(ErrorCode.NOT_FOUND_USER);

// 발생 맥락 포함 - detail 추가
public User findUser(String username) {
    return userRepository.findByUsername(username)
        .orElseThrow(() -> new BusinessLogicException(
            ErrorCode.NOT_FOUND_USER,
            "username '" + username + "'에 해당하는 사용자가 없습니다"
        ));
}

// 복구 데이터 포함 - 클라이언트가 처리에 필요한 부가 정보
throw new BusinessLogicException(
    ErrorCode.DUPLICATE_PROJECT,
    "이미 존재하는 프로젝트 키입니다",
    Map.of("existingProjectKey", "ALM")
);
```

## 3. 인프라 레이어 예외

### 3.1 ExternalApiException

인프라 레이어 예외는 **외부 기술 실패 정보만** 담는다. 비즈니스 판단을 포함하지 않는다.

```java
@Getter
public class ExternalApiException extends RuntimeException {

    private final ErrorCode errorCode;
    private final int upstreamStatus;   // 외부 API가 반환한 HTTP 상태
    private final String upstreamUri;   // 호출한 외부 API 경로
    private final String detail;        // 외부 API 응답 메시지
}
```

### 3.2 사용 예시

```java
// BitbucketAdapter - 인프라 레이어
public List<Project> getProjects(String token) {
    try {
        return bitbucketClient.fetchProjects(token);
    } catch (WebClientResponseException e) {
        throw new BitbucketApiException(
            e.getStatusCode().value(),
            e.getRequest().getURI().toString(),
            e.getResponseBodyAsString()
        );
    }
}
```

### 3.3 인프라 → 서비스 예외 변환 원칙

서비스 레이어와 인프라 레이어의 격리를 원칙으로 한다.  
단, 외부 기술 실패에 **도메인 의미가 필요한 경우**(e.g., 404 → 리소스 없음)에 한해 아래 방식으로 처리한다.

- **포트(Port) 인터페이스**에 해당 변환의 목적을 명확히 문서화한다.
- **어댑터(Adapter)**가 외부 응답 상태를 판단하여 도메인 예외(`BusinessLogicException`)를 던진다.
- 어댑터 내 비즈니스 판단은 **최소화**하며, 단순 상태 코드 매핑 수준에 한정한다.

```java
// ScmPort.java - 포트에 변환 의도 명시
/**
 * 저장소 단건 조회.
 * 404 응답 시 어댑터가 NOT_FOUND_REPOSITORY(BusinessLogicException)를 던진다.
 */
Repository findRepository(String projectKey, String slug);

// BitbucketAdapter.java - 어댑터의 제한적 비즈니스 판단
@Override
public Repository findRepository(String projectKey, String slug) {
    try {
        return bitbucketClient.getRepository(projectKey, slug);
    } catch (BitbucketApiException e) {
        if (e.getUpstreamStatus() == 404) {
            throw new BusinessLogicException(ErrorCode.NOT_FOUND_REPOSITORY);
        }
        throw e;  // 그 외는 인프라 예외 그대로 전파
    }
}
```

## 4. 보안 필터 레이어 예외

Security Filter 레이어는 `DispatcherServlet` 앞단 서블릿 필터 체인에 속하며, `GlobalExceptionHandler(@RestControllerAdvice)`에 도달하지 않는다.
이 레이어의 예외 "핸들러 계약"은 Spring Security의 `ExceptionTranslationFilter → AuthenticationEntryPoint`이다.

### 4.1 SecurityAuthException

```java
// global/exception/SecurityAuthException.java
public class SecurityAuthException extends AuthenticationException {

    private final ErrorCode errorCode;

    public SecurityAuthException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() { return errorCode; }
}
```

- `AuthenticationException` 상속 → `ExceptionTranslationFilter`가 자동으로 `AuthenticationEntryPoint`로 위임
- `ErrorCode` 필드 → `AuthenticationEntryPoint`에서 RFC 9457 응답 구성에 사용
- `BusinessLogicException`과 동일한 원칙 — **직접 사용하는 구체 클래스**, 별도 구현체 없음

### 4.2 사용 예시

```java
// JwtTokenProvider — 보안 유틸리티
throw new SecurityAuthException(ErrorCode.INVALID_TOKEN);   // JWT 위변조·형식 오류
throw new SecurityAuthException(ErrorCode.EXPIRED_TOKEN);   // JWT 만료
```

서비스 레이어가 `new BusinessLogicException(ErrorCode.NOT_FOUND_USER)`를 직접 throw하듯,
보안 필터 레이어도 `new SecurityAuthException(ErrorCode.xxx)` 패턴을 사용한다.
케이스별 구현체(`InvalidTokenException` 등)는 `AuthenticationEntryPoint`가 타입으로 분기해야 할 이유가 생길 때만 생성한다.

### 4.3 AuthenticationEntryPoint 연동

`JwtAuthenticationFilter`가 `SecurityAuthException`을 직접 catch하여 `JwtAuthenticationEntryPoint.commence()`를 호출한다.

`ExceptionTranslationFilter`는 필터 체인상 `JwtAuthenticationFilter`보다 뒤에 위치하므로, `JwtAuthenticationFilter`에서 발생한 예외를 잡지 못한다. 따라서 토큰 검증 예외는 필터 내부에서 직접 EntryPoint로 위임한다.

```java
// JwtAuthenticationFilter.java
if (StringUtils.hasText(jwt)) {
    try {
        if (jwtTokenProvider.validateAccessToken(jwt)) {
            // ... SecurityContext 설정
        }
    } catch (SecurityAuthException e) {
        SecurityContextHolder.clearContext();
        jwtAuthenticationEntryPoint.commence(request, response, e);
        return;
    }
}
```

```java
// JwtAuthenticationEntryPoint.java
ErrorCode errorCode = ErrorCode.UNAUTHORIZED;  // 토큰 없음(InsufficientAuthenticationException) 기본값
if (authException instanceof SecurityAuthException e) {
    errorCode = e.getErrorCode();              // INVALID_TOKEN / EXPIRED_TOKEN
}
```

### 4.4 AccessDeniedHandler 연동

인증은 됐으나 권한이 없는 요청(403)은 `ExceptionTranslationFilter`가 `AccessDeniedException`을 감지하여
`JwtAccessDeniedHandler`로 위임한다.

```java
// JwtAccessDeniedHandler.java
@Override
public void handle(HttpServletRequest request, HttpServletResponse response,
    AccessDeniedException accessDeniedException) throws IOException {

    ErrorCode errorCode = ErrorCode.FORBIDDEN;
    response.setStatus(errorCode.getHttpStatus().value());
    response.setContentType("application/problem+json;charset=UTF-8");
    objectMapper.writeValue(response.getWriter(), ErrorResponse.of(
        errorCode, errorCode.getMessage(), request.getRequestURI(), null));
}
```

```java
// SecurityConfig.java
.exceptionHandling(e -> e
    .authenticationEntryPoint(jwtAuthenticationEntryPoint)  // 401
    .accessDeniedHandler(jwtAccessDeniedHandler))           // 403
```

### 4.5 로깅 책임

보안 필터 레이어의 예외 로깅은 각 핸들러(`JwtAuthenticationEntryPoint`, `JwtAccessDeniedHandler`)에서 1회만 수행한다.
`JwtTokenProvider` 등 하위 유틸리티에서 직접 로깅하지 않는다.

## 5. 예외 처리 흐름

```
Security Filter Layer (DispatcherServlet 이전)
    │  SecurityAuthException 발생 (토큰 만료·위변조)
    ▼
JwtAuthenticationFilter
    │  catch(SecurityAuthException) → EntryPoint 직접 호출
    ▼
JwtAuthenticationEntryPoint
    └── ErrorCode 기반 RFC 9457 응답 → 클라이언트

Security Filter Layer — 토큰 없음 경로
    │  SecurityContext 미설정 상태로 filterChain 통과
    ▼
ExceptionTranslationFilter
    │  AuthorizationFilter의 InsufficientAuthenticationException 감지
    ▼
JwtAuthenticationEntryPoint (UNAUTHORIZED 고정값)
    └── ErrorCode 기반 RFC 9457 응답 → 클라이언트

Security Filter Layer — 권한 없음 경로
    │  SecurityContext에 인증 정보 있음, 권한 부족
    ▼
ExceptionTranslationFilter
    │  AuthorizationFilter의 AccessDeniedException 감지
    ▼
JwtAccessDeniedHandler (FORBIDDEN)
    └── ErrorCode 기반 RFC 9457 응답 → 클라이언트

Service / Infrastructure Layer (DispatcherServlet 이후)
    │  BusinessLogicException, ExternalApiException 발생
    │  + Spring MVC 파싱·검증 오류, 예상치 못한 예외 포함
    ▼
RestControllerAdvice (GlobalExceptionHandler)
    ├── BusinessLogicException  →  warn  + RFC 9457 응답   (명시적 핸들러)
    ├── ExternalApiException    →  error + RFC 9457 응답   (명시적 핸들러)
    ├── Spring MVC 표준 예외    →  warn  + RFC 9457 응답   (ResponseEntityExceptionHandler 오버라이드)
    └── Exception               →  error + 500             (안전망)
```

- **로깅**: 모든 예외 로깅은 각 레이어의 핸들러(`AuthenticationEntryPoint`, `RestControllerAdvice`)에서만 처리한다. 서비스·인프라·보안 유틸리티 레이어에서 직접 로깅하지 않는다.
- **중복 로깅 금지**: 예외를 `catch` 후 재throw하는 경우에도 로깅은 핸들러에서 1회만 수행한다.

### 5.1 GlobalExceptionHandler 핸들러 유형

Spring은 `@ExceptionHandler`에서 던져진 예외 타입에 가장 구체적으로 일치하는 핸들러 메서드를 선택한다.  
GlobalExceptionHandler는 이 매칭 특성을 활용해 아래 세 가지 유형의 핸들러로 구성한다.

**명시적 핸들러 — 도메인/인프라 예외**

각 레이어에서 변환·생성한 예외를 직접 처리한다.

| 예외 | 로그 레벨 | 이유 |
|------|-----------|------|
| `BusinessLogicException` | `warn` | 예상된 비즈니스 오류 — 알람 불필요 |
| `ExternalApiException` (및 하위 타입) | `error` | 외부 시스템 장애 — 운영 알람 필요 |

**Spring MVC 표준 예외 오버라이드**

`ResponseEntityExceptionHandler`를 상속하여 Spring이 내부적으로 발생시키는 예외들을 RFC 9457 포맷으로 오버라이드한다.  
미상속 시 이 예외들이 Spring 기본 포맷(RFC 9457 불일치)으로 응답된다.

| 예외 | 상황 | HTTP |
|------|------|------|
| `MethodArgumentNotValidException` | `@Valid` Bean Validation 실패 | 400 |
| `HttpMessageNotReadableException` | 요청 JSON 파싱 실패 | 400 |
| `ConstraintViolationException` | `@Validated` 메서드 파라미터 검증 실패 | 400 |
| `NoHandlerFoundException` | 존재하지 않는 URI 요청 | 404 |

**안전망 (`Exception.class`)**

예상치 못한 버그성 예외(NPE, ClassCastException 등)를 포착한다.  
`Exception`은 모든 예외의 상위 타입이므로 명시적 핸들러에 매칭되지 않은 것들이 여기서 잡힌다.  
클라이언트에 스택트레이스·내부 경로 등 민감 정보가 노출되지 않도록 `detail` 필드를 포함하지 않는다.

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception e, HttpServletRequest request) {
    log.error("Unhandled exception", e);  // 스택트레이스 포함 error 레벨
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
        .contentType(MediaType.APPLICATION_PROBLEM_JSON)
        .body(ErrorResponse.builder()
            .type("about:blank")
            .title("Internal Server Error")
            .status(500)
            .instance(request.getRequestURI())
            .build());
    // detail에 e.getMessage() 절대 포함 금지 — 내부 구현 정보 노출 위험
}
```

## 6. 응답 데이터 명세 (RFC 9457)

### 6.1 응답 필드

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `type` | `String` | `ErrorCode.typeUri` | 에러 종류 식별 URI. Confluence 문서 없는 경우 `about:blank` 고정 |
| `title` | `String` | `ErrorCode.title` | 에러 종류 고정 요약 (동일 ErrorCode면 항상 동일) |
| `status` | `int` | `ErrorCode.httpStatus` | HTTP 상태 코드 |
| `detail` | `String` | 호출자 주입 or `ErrorCode.title` | 이번 발생의 구체적 맥락 (nullable → title fallback) |
| `instance` | `String` | 요청 URI | 문제가 발생한 요청 경로 |
| `timestamp` | `LocalDateTime` | 핸들러 생성 | 발생 시각 |
| `code` | `String` | `ErrorCode.code` | 프론트엔드 분기 처리용 내부 코드 |
| `data` | `Object` | 호출자 주입 | 클라이언트 복구용 부가 데이터 (nullable) |

> `title`은 `ErrorCode` 단위 고정값이다. 발생 맥락 정보는 반드시 `detail`에 담는다.

### 6.2 응답 예시

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{
  "type": "about:blank",  // Confluence 에러 문서 작성 전까지 about:blank 고정
  "title": "사용자를 찾을 수 없습니다",
  "status": 404,
  "detail": "username 'kim.jeonghyeon'에 해당하는 사용자가 없습니다",
  "instance": "/api/v1/user/token",
  "timestamp": "2026-05-22T10:30:00",
  "code": "U001",
  "data": null
}
```

## 7. 레이어별 책임 요약

```
┌─────────────────────────────────────────────────────┐
│  보안 필터 레이어 (SecurityAuthException)             │
│                                                     │
│  ErrorCode  → 토큰 오류 종류 (INVALID / EXPIRED)    │
│  핸들러     → JwtAuthenticationEntryPoint           │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  서비스 레이어 (BusinessLogicException)              │
│                                                     │
│  ErrorCode → 타입 레벨 정보 (어떤 종류의 오류)        │
│  detail    → 발생 레벨 정보 (이번에 왜 발생했는지)    │
│  data      → 클라이언트가 복구에 필요한 부가 데이터   │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  인프라 레이어 (ExternalApiException)                │
│                                                     │
│  ErrorCode       → 내부 에러 분류                   │
│  upstreamStatus  → 외부 API가 반환한 HTTP 상태       │
│  upstreamUri     → 호출한 외부 API 경로              │
│  detail          → 외부 API 응답 메시지              │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  GlobalExceptionHandler (RestControllerAdvice)       │
│                                                     │
│  명시적  BusinessLogicException → RFC 9457 (warn)  │
│          ExternalApiException  → RFC 9457 (error)  │
│  오버라이드  Spring MVC 표준 예외 (warn)              │
│             ResponseEntityExceptionHandler 상속      │
│  안전망  Exception → 500 (error)                    │
└─────────────────────────────────────────────────────┘
```

---

## 8. 금지 패턴

| 패턴 | 이유 |
|---|---|
| 서비스 레이어에서 `ExternalApiException` catch 없이 외부 호출 | 인프라 예외가 서비스 계약을 오염시킴 |
| 어댑터에서 복잡한 비즈니스 로직 수행 | 어댑터는 변환과 단순 상태 매핑만 담당 |
| 서비스·인프라·보안 유틸리티 레이어에서 직접 로깅 | 중복 로깅 방지, 핸들러 단일 책임 |
| `ErrorCode` 없이 메시지 문자열만으로 예외 생성 | 클라이언트 분기 처리 불가, 일관성 깨짐 |
| `title`에 발생 맥락 정보 포함 | `title`은 ErrorCode 고정값, 맥락은 `detail`에 |
| `JwtAuthenticationFilter`에서 토큰 예외를 직접 catch해 응답 작성 | `AuthenticationEntryPoint` 책임 침해, 관심사 혼재 |
| `GlobalExceptionHandler`가 `ResponseEntityExceptionHandler` 미상속 | Spring MVC 표준 예외가 RFC 9457 불일치 포맷으로 응답됨 |
| `Exception` 안전망 핸들러에서 `e.getMessage()`를 `detail`에 포함 | 내부 구현 정보·경로 등 민감 정보 클라이언트 노출 |

## 9. 체크리스트

새 예외 추가 시 아래 항목을 확인한다.

- [ ] `ErrorCode`에 신규 항목 추가 (code prefix 체계 준수)
- [ ] `typeUri` 경로 일관성 확인 (`/errors/{kebab-case}`)
- [ ] 상속 구현체 생성 여부 판단 (기준: §2.3 / §4.2)
- [ ] 인프라 → 서비스 변환 필요 시 포트에 주석 명시
- [ ] `RestControllerAdvice` 또는 `AuthenticationEntryPoint` 핸들러 등록 여부 확인
